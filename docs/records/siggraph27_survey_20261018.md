> 日期 2026-10-18。目标会议 SIGGRAPH 2027（按惯例 2027 年 1 月下旬截稿，约 14 周）。
> 本文所有断言标注来源等级：**[摘要级]** 由 arXiv 摘要直接核实；**[正文级]** 由项目组全文核对，本轮未复核；**[实测]** 由本仓库诊断数据重新提取。

## 0. 一句话结论

现有全地形 locomotion 的地形条件**全部停在 2.5D**。当体积条件与 2.5D 条件并存时，体积支路会被系统性忽略——根因是**输入冗余 + 零初始化残差**，不是表达能力不足。修法不是加更多体积，而是**正交化条件输入**。这个现象在两个独立系统上重现，因此它是一个可命名的现象，而不是我们的 bug。

## 2. 真正的空隙：全行业共识性的 2.5D 妥协

证据全在它们自己的措辞里 [摘要级]：

- PASSAGE：`robot-centric multi-layer elevation map`
- Terrain Traversal：`sensed elevation grid`
- SceMoS：`2D local scene heightmap ... without full 3D volumetric reasoning`
- MTC / PHP：落脚点 / 高程
- BRACE：`terrain conformance lifts footholds and root onto the local surface`

**所有人都知道高程图不表达悬垂与天花板，但所有人都因为规划方便而接受它。他们的设计选择本身就是我们的 motivation。**

同时，机器人侧优化的是通过率（68.9%–90%），人体生成侧优化的是 realism/contact accuracy——**没有任何一篇从感知与运动质量的轴去评价地形条件**。这是 SIGGRAPH 的轴，目前是空的。

## 3. 我们自己的实测证据

数据来源：`out/parc_rugged32_20261013_v2/native_terrain_gaps_20261015_v1/`，本轮从 `conditions.json` 重新提取。

### 3.1 先澄清两个被混淆的量 [实测]

| 字段 | 含义 | 用途 |
|---|---|---|
| `geometry_comparison.*_height_max_difference_m` | 楼梯场景 vs 平面场景的**几何响应差** | **衰减结论用这个** |
| `actual_*_height_change_m` | 同一场景内根从第 3 帧到第 27 帧的**自身上升** | 内部自洽性，比值≈1.0 |

两者数值差异极大。论文必须同时报，否则审稿人会把「根传导完好」误读成「没有衰减」。

### 3.2 几何响应是**各向异性且相位相关**的 [实测]

| entry | start | planner Δ(mm) | decoded Δ(mm) | 保留率 |
|---|---:|---:|---:|---:|
| up | 24 | 133.96 | 2.22 | **1.7%** |
| up | 16 | 13.31 | 0.70 | 5.3% |
| up | 36 | 363.52 | 25.68 | 7.1% |
| up | 32 | 377.81 | 60.31 | 16.0% |
| up | 40 | 255.93 | 64.29 | 25.1% |
| up | 48 | 235.98 | 113.39 | **48.1%** |
| down | 0 | 6.23 | 0.34 | 5.5% |
| down | 16 | 198.96 | 66.23 | 33.3% |
| down | 24 | 392.24 | 226.41 | **57.7%** |
| down | 32 | 692.99 | 589.22 | **85.0%** |
| down | 36 | 819.37 | 472.78 | 57.7% |
| down | 48 | 394.68 | 26.63 | **6.7%** |

三个结论：

1. **上行衰减远大于下行**：planner 响应几乎相同的两行（up-32: 377.81 vs down-24: 392.24），保留率 16.0% vs 57.7%，**差 3.6 倍**。
2. **保留率随窗口起点系统性变化**，不是常数增益，是过程相关。
3. **可证伪的机制假设**：若抹平来自平地先验对「抬升身体」的抵抗，则要求的抬升越大、保留越少；据此**头顶限高（蹲伏）应当比上行衰减更严重**。这条预测可用 M2 数据直接检验。

### 3.3 体积支路在 Pose 阶段实质**完全惰性** [实测]

原文报告为 0.10%（1/1024）。逐窗口重提取后更准确的说法是：

- **15/16 个楼梯窗口，体积支路改变 0 个 token**
- 仅 down-24 改 1 个，腿部差 0.455 mm
- 对照：旧高度场支路每窗口改 2–9 个 token，腿部差 3.1–8.8 mm

即 **16 个窗口合计只有 1 个 token 变化**。这不是「贡献小」，是「没参与」。

### 3.4 架构给出了因果 [实测，代码级]

`motionbricks/data/unified_terrain.py`：

```python
class UnifiedSceneResidual(nn.Module):
    self.output = nn.Linear(128, width, bias=False)
    nn.init.zeros_(self.output.weight)      # 零初始化残差
    return value + self.output(delta)        # 初始化时恒等
```

结构事实：

1. **没有独立 gate**——可学习缩放就是 `output.weight` 本身。
2. **四个 stage（root_stage1 / stage2 / pose / decoder）共用同一份 `self.memory`**（`SharedTerrainEncoder(volume_observation)` 输出），旧高度场走原生 `pose._terrain_cross_attention`，两条路在同一 attention 内竞争。

**几十秒就能测的判定量**：

```
||controller.adaptation['pose'].output.weight||
```

- 接近 0 → 分支根本没长起来：**优化 / 数据问题**
- 量级正常 → 权重长起来但 attention 输出退化：**冗余遮蔽**

这两个结论对应完全不同的论文与修法，必须在任何训练之前先测。

### 3.5 数据审计是当前最大的混杂源 [实测，引自 native_terrain_gap_audit_20261015.md]

- 88 个训练窗口，满足「历史 <0.1 m/s → 目标 >0.5 m/s」起步条件的只有 **2 个**，楼梯中 **0 个**
- 楼梯 terminal 速度集中在 1.87–3.73 m/s，**没有 0.8–1.6 m/s 低速楼梯**
- 一条被标为 walk 的动作（`bones:ad5d0f45...`）97 帧根位移仅 **3.92 mm**，实际来自 `bones:walk_backward_start`
- 20 次闭环 rollout 全线通过 **0/20**；bank 外 8 条首台阶 0/8

**在这个 bank 上得出的任何架构结论都不可信**，包括「体积支路没用」。

## 4. 核心论点

> **体积条件被忽略不是容量问题，是冗余问题。**
> 当体积场与高度场同时作为条件输入，且高度场已能解释训练分布上的方差时，零初始化残差不会被训练起来——winner-take-all。
> 解法是把体积支路的输入**正交化**：只喂高度场在原理上无法表达的量（头顶净空、侧向净空、悬垂符号），使该支路在开放地形上恒为零、在受限地形上独占信号。

### 4.1 与已发表负结果的统一

[Terrain Traversal Without Motion Priors](https://arxiv.org/abs/2610.14061) 报告：无标签 MoE 路由器在所有地形上塌缩到近均匀（≈0.20），自监督地形潜变量仅得 2.6% 成功率（特权标签 15.3%，完整系统 90%）[摘要级]。

这与我们的 1/1024 是**同一现象**：当条件是冗余的，门控没有梯度信号去分化。

**这个统一使论文从「我们做了个系统」升级为「我们命名并解释了一个现象」**——这是 SIGGRAPH 更认的形态。

### 4.2 可证伪判据

| 假设 | 判据 | 失败即证伪 |
|---|---|---|
| 零初始化残差未被训练 | `||W_pose|| ≈ 0` | 范数正常 → 假设错 |
| 冗余导致惰性 | 假顶棚探针下 token 仍不变 | token 变化 → 分支活着，问题在别处 |
| 抬升抵抗假说 | 蹲伏保留率 < 上行保留率 | 否则衰减另有原因 |
| 正交化可修复 | 正交输入下体积支路 token 变化显著上升 | 无上升 → 需换架构 |

## 6. 实验设计

### 6.1 零训练前置探针（本周，成本最低，决定方向）

1. 打印 `adaptation['pose']`、`root_stage1/2`、`decoder` 四个 `output.weight` 的范数
2. 平地 BONES 窗口 + 合成假顶棚（仅改体积查询）→ 观察 token 变化与输出
3. 已有 16 楼梯窗口的保留率表（本文档已给出）

### 6.2 受控修复后的小样本对照（1 seed 迭代，最终 3 seeds 出表）

- 数据清洗：活动区间裁剪、速度/朝向过滤、补齐平地正向起步与 0.8–1.6 m/s 低速楼梯
- 正交化体积输入 vs 原始体积输入，其余完全一致
- 指标：分支活性（token 变化率）、几何响应保留率、mesh 级穿透、闭环通过率

### 6.3 外部零样本验证

使用 [MTC](https://arxiv.org/abs/2603.05993) 的 145 个场景 / 348 条轨迹作为**非自建**验证集。这直接解掉「所有地形都是程序化生成」这一最省事的拒稿理由。

### 6.4 评测指标

| 维度 | 指标 |
|---|---|
| 接触保真 | 18056 顶点 8-substep 峰值穿入、按身体部位分解的穿透率 |
| 支撑质量 | 腿部误差 ≤1.5 cm、Root RMS ≤2 cm、滑步 mm/frame |
| 泛化 | MTC 零样本通过率、按难度参数的失效边界 |
| 几何响应 | 上行/下行/蹲伏的保留率传递函数 |
| 长时序 | 16–60 s 自回归漂移与恢复时间分布 |
| 效率 | 端到端延迟、1536 点查询开销、显存 |
| 感知 | 穿透可见性阈值（按部位、按镜头距离） |

### 6.5 Baselines

1. 当前 28942（2.5D + 体积并存，即坍缩态）
2. 仅 2.5D 高度场
3. 正交化体积输入（本方法）
4. 本方法 + SceMoS 式轨迹后处理（用于证明我们不靠后处理）

## 10. 与 MotionBricks 原论文的定位关系

[MotionBricks](https://arxiv.org/abs/2604.24833)（Wang et al., 2026-04）[摘要级] 以 Smart Object 原语跨越障碍。本工作废除人工地形关键帧、以原生 3D 场景场驱动 `Root → Pose → Decoder`，是该论文 limitation 指出的正统续作方向。这一点应作为 positioning 明写，而不是隐含。
